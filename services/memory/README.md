# Zoe memory worker

This service exposes person-scoped memory through HTTP only. Memory lives in Mem0 with Qdrant vectors and a local history database. There is no claim index, polling loop, control-plane client, deletion-only mode, or job accounting.

Dependency versions are locked in [pyproject.toml](pyproject.toml) and [uv.lock](uv.lock). [config.py](config.py) pins the multilingual embedding revision and dimension; [embedding.py](embedding.py) checks model artifacts. [mem0_backend.py](mem0_backend.py) constructs Mem0 with the pinned embedder and Responses LLM adapter. [Compose](docker-compose.yml) persists Qdrant, Mem0 history, person ownership metadata, and model cache under `ZOE_MEMORY_DATA_ROOT`; it mounts the API token as a file secret. Existing claim-scoped data is not migrated: deployment wipes the test machine's Mem0/Qdrant data.

## Process and configuration

Run `python -m services.memory.worker`. When `ZOE_MEMORY_API_TOKEN_FILE` is unset, `main()` logs one error and exits nonzero before constructing the backend. Otherwise it builds Mem0 and serves HTTP in the main thread; SIGTERM requests shutdown from a separate thread, closes the listener, restores the previous signal handler, and closes the history database. The Responses adapter dispatches directly with SDK retries disabled; request timeout context variables bound HTTP-triggered LLM calls.

The worker reads `ZOE_MEMORY_API_TOKEN_FILE`, `ZOE_MEMORY_API_ADDR`, `ZOE_MEMORY_API_TIMEOUT_SECONDS`, `ZOE_QDRANT_URL`, `ZOE_QDRANT_API_KEY`, `ZOE_MEM0_COLLECTION`, `ZOE_MEM0_HISTORY_DB`, `ZOE_MEM0_LLM_PROVIDER` (only `openai`), `ZOE_MEM0_LLM_MODEL` (required), `ZOE_MEM0_LLM_BASE_URL`, `ZOE_MEM0_LLM_API_KEY`, `ZOE_MEM0_LLM_REASONING_EFFORT`, `ZOE_MEMORY_MODEL_CACHE`, `FASTEMBED_CACHE_PATH`, and `ZOE_LOG_LEVEL`. Obsolete polling/control/runner/claim-collection environment settings are ignored. Mem0 telemetry is forcibly disabled before import.

## Internal person memory API

The standard-library HTTP listener uses `ZOE_MEMORY_API_ADDR` (default `0.0.0.0:8788`). All routes, including `GET /healthz`, require bearer authentication. POST JSON bodies are limited to 64 KiB except `/v1/memory/ingest`, which allows 256 KiB (including JSON framing, measured in bytes); `ZOE_MEMORY_API_TIMEOUT_SECONDS` bounds responses (default 60, maximum 120). In-flight backend operations cannot be forcibly interrupted; mutation outcomes after timeouts are uncertain, so callers must not blindly retry writes or ingestion. Concurrency is bounded and new mutations check the deadline before dispatch.

For person-scoped requests, the caller supplies an opaque `user` encoding workspace plus owner subject, never claim identity. The worker hashes it into a separate `zoe-person-` namespace. `POST /v1/memory/search` accepts `{user,query,top_k?}` (default 8, maximum 20), uses no LLM, and returns `{items:[{id,text,score}]}`. `POST /v1/memory/write` accepts `{user,sentence,restatement}`, recalls five memories, makes one configured LLM call, validates all operations before applying them, and returns `{operations:[{op,id?,text}]}`. Replacement references are exact memory text, not model-visible IDs or aliases; unmatched or ambiguous references become adds. `POST /v1/memory/delete-all` accepts `{user}` and removes vectors plus history/messages scoped through a durable ID-only person ownership ledger. Unknown pre-ledger history cannot be attributed safely and is not globally purged.

For transcript ingestion, `POST /v1/memory/ingest` accepts exactly `{user,text}` with nonempty, non-whitespace string fields. The `text` is conversation transcript data, including completed tasks as original requests and results, not instructions. Invalid input returns HTTP 400 `{error_kind:"request_invalid"}` before Mem0 is called. The handler makes one Mem0 `add(text, user_id=person_user_id(user), infer=True, prompt=INGEST_INSTRUCTIONS)` call; Mem0 extracts durable self-stated user facts/preferences, excluding assistant statements and task content except durable outcomes stated by the user. [INGEST_INSTRUCTIONS](person_memory.py) defines these categories without examples or behavioral requirements. The response is HTTP 200 `{added:int,updated:int}`, counting `ADD` and `UPDATE` result events; empty extraction returns zeros. Ingestion shares write's person ownership/history tracking, deletion scope, serialization, and deadline handling.

For writes and ingestion, no job headers or job-scoped ledger are used. Write calls the configured LLM once; ingestion uses Mem0's inference workflow.

When `ZOE_LOG_LEVEL=debug` (default `info`), Zoe logs search query/results, complete write model input/output, ingest text/instructions and Mem0 results, and permits Mem0 content logs. At INFO, each synchronous LLM call logs only `memory_api llm_call component=<memory_write|memory_ingest> status=<ok|error> error_kind=<none|backend_unavailable|deadline_exceeded> elapsed_ms=<duration>`; requests log fixed request-kind labels (`ingest` for ingestion), status, and duration. Neither INFO record includes content, user IDs, credentials, or raw exception messages. HTTP client debug logging remains disabled to protect credentials.
